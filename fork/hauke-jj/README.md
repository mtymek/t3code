# Carrying Hauke's jj patch

This fork takes jj support from [HaukeSchnau/t3code](https://github.com/HaukeSchnau/t3code) and nothing else from it. Hauke's `main` carries about 60 other patches and renumbers upstream's database migrations, so this fork never merges it. `sync.ts` rebuilds one commit that holds only the jj patch, on top of an upstream release tag.

Hauke describes the patch in `patches/jujutsu.md`, which this fork carries. Read that file first after every sync.

## Stack

```
v0.1.9                      upstream release tag
└─ hauke-jj-tooling         this directory
   └─ hauke-jj              generated by sync.ts; never edit by hand
      └─ jj-glue            local code that replaces Hauke patches the jj code depends on
         └─ main            your own work
```

- `hauke-jj` is regenerated from scratch on every sync. Hand edits to it are lost.
- `jj-glue` holds the changes this fork needs because it leaves Hauke's other patches out:
  - `ManagedWorkspaces.ts` keeps only the jj backend of Hauke's workspaces patch.
  - `ProviderThreadEnvironment.ts` drops Hauke's skill packs.
  - `server.ts` and `ws.ts` wire those in and route fork workspace removal through `jj workspace forget`.
- Put your own work above `jj-glue`. jj rebases it whenever the layers below change.

## How the patch is selected

`config.json` defines what counts as the jj patch:

- **`owned`:** files taken whole from Hauke's fork, such as everything under `apps/server/src/jj/`.
- **`extraJjCommits`:** jj commits that touch no owned file, such as the adapter work that reports changed paths and command cwd.
- **`hookFiles`:** upstream files with jj hooks that only Hauke's merges touched.
- **`signals`:** identifiers the jj patch introduces.
- **`excluded`:** files that belong to Hauke's other patches, each with the reason.

For every other file that a jj commit touched, `sync.ts` diffs Hauke's `main` against his upstream merge base and classifies each hunk with `git blame`:

- A hunk is asked about when a jj commit wrote it, when it names a signal, or, in a hook file, when a merge wrote it.
- Every other hunk is left out without asking.
- Decisions are stored in `decisions.json`, keyed by a hash of the hunk's changed lines.
- A hunk that mixes jj lines with another patch's lines is stored as a trimmed copy (`"text"`).
- A decision is reused for as long as Hauke's hunk keeps the same changed lines, so a sync only asks about hunks he changed.

## Update to a new upstream release and Hauke's latest jj work

Run these from the root of this checkout.

1. Fetch both remotes:
   ```sh
   jj git fetch --remote upstream
   jj git fetch --remote hauke
   ```
2. See what Hauke changed since the last port, and whether he has merged the release you want:
   ```sh
   node fork/hauke-jj/sync.ts status
   ```
   - `hauke base` is the upstream commit Hauke last merged.
   - Build onto a release tag at or below that commit. Hauke's code then compiles against the upstream code it was written for.
   - If the release you want is newer than Hauke's base, wait for his next sync, or build anyway and fix what breaks in `jj-glue`.
   - `status` also lists new jj-named files. Add each one to `owned` or `excluded` in `config.json`.
3. Decide the new hunks:
   ```sh
   node fork/hauke-jj/sync.ts hunks           # undecided hunks, with the commits that wrote them
   node fork/hauke-jj/sync.ts take <key>...
   node fork/hauke-jj/sync.ts skip <key>...
   ```
   For a mixed hunk, trim it and take the trimmed copy:
   ```sh
   node fork/hauke-jj/sync.ts show <key> > /tmp/hunk.patch
   $EDITOR /tmp/hunk.patch
   node fork/hauke-jj/sync.ts take <key> --edited /tmp/hunk.patch
   ```
4. Rebuild and restack:
   ```sh
   node fork/hauke-jj/sync.ts build --onto v0.1.10
   ```
   - The build makes the new `hauke-jj` commit in a temporary jj workspace, on Hauke's upstream base, where every hunk applies cleanly.
   - It then rebases `hauke-jj-tooling` onto the tag and the new `hauke-jj` onto `hauke-jj-tooling`, moves `jj-glue` and everything above it onto the new commit, and abandons the old one.
   - It finishes by listing commits with conflicts. Resolve those in `jj-glue` or in your own commits, never in `hauke-jj`.
   - The build writes `state.json` and moves any changes under `fork/hauke-jj` into `hauke-jj-tooling`.
5. Run `node fork/hauke-jj/sync.ts prune` to drop decisions for hunks Hauke no longer has.
6. Verify:
   ```sh
   vp i
   vp run typecheck
   vp test run apps/server/src/jj apps/server/src/vcs
   ```

## Taking more of Hauke's work

- **A whole file:** add it to `owned`.
- **Hunks in a file that is not scanned:** add the file to `hookFiles`, then decide its hunks.
- **Another commit of Hauke's:** add it to `extraJjCommits`. Its hunks are then always asked about.
